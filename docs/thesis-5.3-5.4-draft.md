## 5.3. Розробка програмного модуля

Програмний модуль реалізує запропонований у розділі 4 метод оцінювання ризику безпеки туристичної подорожі — оператор T₅(R, E, Ξ, Δ, M_I, M_R1, M_R2, M_R3) → Y(f₅) = {μ_R, T_R} — у вигляді вебзастосунку для особи, що приймає рішення (ОПР), та відкритої програмної бібліотеки обчислювального ядра. Відповідно до архітектури інтелектуальної аналітичної платформи модуль є автономним: він не залежить від інших модулів системи (оператори T₁–T₄ не входять до його складу), що дозволяє застосовувати його як самостійний інструмент підтримки прийняття рішень.

### 5.3.1. Архітектура та технологічний стек

Програмний модуль побудовано за трирівневою клієнт-серверною архітектурою (рис. 5.1):

```
┌────────────── Клієнтська частина: React + TypeScript ─────────────┐
│  Регіони та дані │ Панель ОПР │ Дашборд │ Параметри  (i18n uk/en) │
└───────────────────────────────┬────────────────────────────────────┘
                          REST API (JSON)
┌───────────────────────────────┴────────────────────────────────────┐
│              Серверна частина: Python 3.12 + FastAPI                │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │   Обчислювальне ядро (окремий пакет tourism-risk):             │ │
│  │   M_I → M_R1 → M_R2 → M_R3 → модуль підтримки прийняття рішень │ │
│  └────────────────────────────────────────────────────────────────┘ │
│  Імпорт Excel/CSV (openpyxl)  │  Експорт звітів (XLSX/PDF)          │
└───────────────────────────────┬────────────────────────────────────┘
                       СУБД: SQLite (→ PostgreSQL)
       (регіони, анкети, критерії, параметри, правила, результати)
```

Рис. 5.1. Архітектура програмного модуля оцінювання ризику безпеки туристичної подорожі

Обґрунтування вибору технологій:

- **Серверна частина — Python 3.12 + FastAPI.** Python є природним середовищем для реалізації апарату нечіткої математики та опрацювання табличних даних опитувань (читання Excel-файлів засобами openpyxl); FastAPI забезпечує типізований REST-інтерфейс із автоматично генерованою документацією (Swagger/OpenAPI), що спрощує верифікацію програмного інтерфейсу та повторне використання модуля.
- **Клієнтська частина — React 19 + TypeScript.** Односторінковий застосунок із суворою статичною типізацією; візуалізація — бібліотека Recharts; інтернаціоналізація — react-i18next (українська та англійська мови).
- **СУБД — SQLite** на етапі розроблення та демонстрації (нульова конфігурація, збереження даних у файлі) з можливістю переходу на PostgreSQL без зміни коду застосунку (ORM SQLAlchemy 2.0).
- **Розгортання** — два шляхи: публічне демонстраційне розгортання на платформі Cloudflare (Worker роздає клієнтську частину як статичні ресурси та маршрутизує запити `/api/*` до контейнера серверної частини; розгортання автоматизоване конвеєром CI/CD GitHub Actions, який при кожній зміні основної гілки виконує повний набір перевірок якості й публікує нову версію) та Docker Compose (контейнери API та вебсервера nginx) для самостійного розгортання з персистентними даними, що забезпечує запуск платформи однією командою.

### 5.3.2. Обчислювальне ядро як відкрита наукова бібліотека

Центральним архітектурним рішенням є виокремлення обчислювального ядра в самостійний програмний пакет **tourism-risk** — реалізацію модулів M_I, M_R1, M_R2, M_R3 (формули (4.2)–(4.9)) мовою Python без жодних зовнішніх залежностей (pure Python, zero-dependency, Python ≥ 3.12). Пакет:

- не залежить від вебзастосунку та СУБД — його можна застосовувати безпосередньо в наукових розрахунках, у середовищах Jupyter, у власних програмних системах інших дослідників і менеджерів туристичної галузі;
- розповсюджується за вільною ліцензією MIT із англомовною документацією, що містить повний виклад формул моделі та приклади відтворення контрольного розрахунку;
- містить файл метаданих цитування CITATION.cff (із посиланням на статтю, в якій опубліковано метод) і підготовлений до публікації в офіційному репозиторії пакетів Python (PyPI), що робить бібліотеку самостійним науковим програмним продуктом, придатним для цитування;
- усі вхідні дані валідуються з інформативними повідомленнями про помилки (діапазони оцінок, монотонність меж інтервалів, коректність патернів правил тощо).

Вебзастосунок використовує бібліотеку як звичайну залежність: серверна частина не містить власної реалізації формул, а звертається до єдиного джерела математичної істини — ядра. Це гарантує тотожність результатів, отриманих через інтерфейс платформи та при безпосередньому використанні бібліотеки.

### 5.3.3. Модель даних

Основні сутності бази даних програмного модуля:

- **Регіон (Region)** — об'єкт оцінювання: назва українською та англійською, прогнозований рівень повторних відвідувань Ξ ∈ [0; 1], експертний рівень безпеки Δ (Δ₁–Δ₅). Кількість регіонів довільна; регіони створюються та вилучаються через інтерфейс.
- **Анкета респондента (Respondent)** — учасник туристичної діяльності: регіон, рік і місяць опитування, тип розміщення, а також оцінки за критеріями у вигляді відображення «код критерію → бал 1–5» (K₁₁–K₃₅).
- **Групи та критерії (CriteriaGroup / Criterion)** — довідник груп критеріїв та їхнього складу (відкритий до розширення); стандартний набір — три групи: G₁ «інфраструктурна безпека» (5 критеріїв), G₂ «соціальна та екологічна безпека» (7), G₃ «медична безпека» (5).
- **Конфігурація платформи (PlatformConfig)** — версіоновані параметри моделі: множники меж термів, шкала χ, параметри Z-сплайна, параметри конусоподібної функції належності, межі інтервалів a₁–a₆, пороги лінгвістичної інтерпретації T_R.
- **Набір правил (RuleSet / Rule)** — версіоновані правила агрегування M_R1 «Якщо–Тоді» з пріоритетом застосування та правилом за замовчуванням; стандартний набір — п'ять правил зі статті.
- **Запуск оцінювання (EvaluationRun)** — результат застосування оператора T₅: усі проміжні величини (розподіл r*(e), δ, φ, m_S, ω, μ_R, T_R) разом зі знімками конфігурації та набору правил, чинних на момент обчислення, що забезпечує повну відтворюваність кожного результату.

Рис. 5.2. Сторінка «Регіони та дані» (файл: docs/screenshots/regions-uk.png)

### 5.3.5. Адаптивність і налаштовуваність моделі

Відповідно до вимоги адаптивності, сформульованої в розділі 4, жодна константа моделі не зафіксована в програмному коді — всі вони є параметрами часу виконання з типовими значеннями зі статті:

| Параметр моделі (розділ 4) | Типове значення | Налаштування |
|---|---|---|
| Склад груп та критеріїв G₁–G₃, K₁₁–K₃₅ | 3 групи, 17 критеріїв | редактор критеріїв |
| Множники меж термів T₁–T₅ (характеристична функція, (4.3)) | 1, 2, 3, 4 (×m_g) | конфігурація |
| Шкала χ для термів r* ((4.5)) | 15 / 30 / 50 / 80 / 100 | конфігурація |
| Параметри Z-сплайна a, b ((4.6)) | 60, 100 | конфігурація |
| Основа та масштаб конусоподібної ФН ((4.7)) | (1; 1), (2; 2) | конфігурація |
| Межі інтервалів a₁–a₆ ((4.8), (4.9)) | 0, 20, 40, 60, 80, 100 | конфігурація |
| Пороги лінгвістичної інтерпретації T_R | 0.2 / 0.4 / 0.6 / 0.8 | конфігурація |
| Правила агрегування M_R1 ((4.4)) | 5 правил зі статті | конструктор «Якщо–Тоді» |

Конфігурація та набори правил **версіонуються**: кожне збереження створює нову активну версію, попередні версії зберігаються та можуть бути активовані повторно. Кожен запуск оцінювання фіксує знімок чинних параметрів, що гарантує відтворюваність результатів і дає змогу коректно порівнювати запуски, виконані за різних налаштувань. У такий спосіб реалізовано контур підтримки прийняття рішень: ОПР аналізує результат, за потреби коригує параметри або правила і повторює оцінювання.

Конструктор правил «Якщо–Тоді» дозволяє ОПР змінювати склад, пріоритет і вихідні терми правил агрегування M_R1: кожне правило задається набором слотів із мінімальними рівнями термів (семантика «не нижче»), правила застосовуються згори вниз до першого спрацювання, а за відсутності збігів діє правило за замовчуванням (типово — H, консервативна оцінка високого індивідуального ризику). Передбачено відновлення стандартного набору правил зі статті однією дією.

### 5.3.6. Двомовність інтерфейсу та експорт результатів

Інтерфейс платформи повністю двомовний (українська/англійська): локалізовано всі елементи інтерфейсу, назви термів (l₁–l₅, L–H, Δ₁–Δ₅, R₁–R₅), тексти критеріїв і повідомлення про помилки; мова перемикається в заголовку та зберігається між сеансами. Результати оцінювання експортуються обраною мовою у двох форматах: **XLSX** (зведений аркуш порівняння регіонів та окремі аркуші з індивідуальними проміжними результатами кожного респондента) і **PDF** (підсумковий звіт із таблицею порівняння, використаними параметрами та інтерпретаціями T_R; для коректного відтворення кирилиці вбудовано шрифти DejaVu). Експортовані звіти призначені, зокрема, для включення в додатки до дисертації.

## 5.4. Верифікація і тестування

Верифікацію програмного модуля виконано на двох рівнях: (1) відтворення контрольного розрахунку методу з розділу 4 та (2) обчислення над реальним набором даних опитування 327 респондентів. Коректність закріплено автоматизованими тестами: **175 модульних тестів обчислювального ядра** та **48 інтеграційних тестів серверної частини** (разом 223), які виконуються при кожній зміні програмного коду.

### 5.4.2. Верифікація на реальному наборі даних

Другий рівень верифікації — обчислення платформи над повним набором даних опитування («Експертне оцінювання.xlsx», 327 респондентів). Вхідні дані ОПР задано згідно зі статтею: Ξ = 0.85 / 0.78 / 0.88, Δ = Δ₅ / Δ₄ / Δ₄. Результати наведено в табл. 5.2.

Числові значення з розділу 4 є ілюстративним прикладом методу; обчислення платформи над реальною вибіркою (n = 327) наведені нижче.

### 5.4.3. Чутливість до вхідних даних ОПР

На цьому наборі даних відмінності між регіонами визначаються переважно вхідними даними ОПР — Ξ і Δ: оскільки δ(R) < a = 60 для всіх регіонів, Z-сплайн насичується (φ = 1) і m_S(R) зводиться до 1 − (1 − Ξ)/2. Це є обґрунтованою властивістю підтримки прийняття рішень: анкетний сигнал свідчить «безпечно скрізь», а диференціацію забезпечують експертні входи. Водночас доцільно супроводити результат коротким аналізом чутливості (наприклад, варіюванням Ξ ∈ [0.5; 1] за фіксованих інших параметрів), який демонструє монотонний вплив Ξ на μ_R та межі, за яких змінюється клас T_R.

> **Примітка для автора.** Аналіз чутливості варто підготувати до захисту — він знімає очікуване питання про роль експертних входів за насиченого φ. Платформа дозволяє виконати його безпосередньо (зміна Ξ на панелі ОПР і повторні запуски зберігаються в історії).

### 5.4.4. Уточнення, виявлені під час формалізації моделі

Програмна формалізація методу — переведення тексту розділу 4 у строгі специфікації та тести — виявила три уточнення, які доцільно зафіксувати (і узгодити з науковим керівником перед остаточним редагуванням тексту дисертації):

1. **Формулювання правила 4 агрегування M_R1.** Текстове формулювання правила («дві групи з термом T₃ та одна з T₂») не узгоджується з опублікованим контрольним прикладом: для респондента e₁ з термами (T₃, T₂, T₂) опубліковано r*(e₁) = AA, що вимагає патерна [T₃, T₂, T₂]. У реалізації за стандартний прийнято варіант, узгоджений із контрольним прикладом; текстовий варіант [T₃, T₃, T₂] ОПР може відновити в конструкторі правил.
2. **Опубліковані значення φ.** Точне значення Z-сплайна φ(79.54) = 0.5227 (опубліковано 0.5 — округлення до однієї десяткової, перенесене далі ланцюжком), а φ(87.89) = 0.1833, тоді як опубліковане 0.13 відповідає δ = 89.78 (імовірна перестановка цифр у значенні δ). Тести реалізації перевіряють і точні значення формули, і відтворення опублікованого ланцюжка.
3. **Статус опублікованих регіональних значень δ.** Опубліковані значення δ = 79.54 / 69.73 / 87.89 не виводяться з файлу опитування за жодним із перевірених способів агрегування (зокрема, жоден агрегат не розділяє R₂ і R₃ більш ніж на 0.1, тоді як опубліковані значення відрізняються на 18.16). Отже, опублікований ланцюжок δ → φ → m_S → ω → μ_R слід трактувати як ілюстративний числовий приклад методу (як і табл. 4.1), а не як обчислення над цією вибіркою; емпіричним застосуванням методу є результати табл. 5.2.

> **Примітка для автора.** У тексті дисертації пункт 3 можна відобразити одним чесним реченням (як на початку п. 5.4.2) або сильнішим варіантом: замінити ілюстративну регіональну таблицю в 5.4 таблицею реальних результатів платформи, залишивши ілюстративний приклад лише в розділі 4.

### 5.4.5. Засоби автоматизованого тестування

Якість програмного модуля підтримується такими засобами:

- **обчислювальне ядро** — 175 модульних тестів (pytest): контрольні значення прикладу зі статті, точні оракули формул (4.6)–(4.9), властивості функцій належності, валідація вхідних даних, регресійні тести реального набору (кількості 209/41/77, значення δ з точністю ±0.01, валідність 327/327 рядків);
- **серверна частина** — 44 інтеграційні тести (pytest + HTTP-клієнт): CRUD-операції, імпорт (включно з помилковими рядками), наскрізний сценарій оцінювання проти контрольних значень, версіонування конфігурацій і правил, перевірка експорту;
- **статичний контроль** — лінтери ruff (Python) і ESLint та компілятор TypeScript у суворому режимі (клієнтська частина);
- **відтворюваність верифікації** — скрипт перевірки набору даних (`uv run --project core python core/scripts/verify_dataset.py`) формує звіт, ідентичний наведеним вище результатам.
