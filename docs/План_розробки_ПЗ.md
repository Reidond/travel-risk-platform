# План розробки ПЗ: веб-додаток «Інтелектуально-аналітична платформа оцінки ризику безпеки туристичної подорожі»

**Основа:** Розділ 4 дисертації (Шафар_PhD.docx) = стаття Шафар_фін.docx
**Призначення в дисертації:** результат розробки закриває підрозділ 5.3 «Розробка програмного модулю» та живить підрозділ 5.4 «Верифікація та тестування»

## 1. Мета ПЗ

Програмна реалізація оператора **T₅(R, E, Ξ, Δ, M_I, M_R1, M_R2, M_R3) → Y(f₅) = {μ_R, T_R}** — обчислення кількісної (μ_R) та лінгвістичної (T_R) оцінки ризику безпеки туристичної подорожі на основі:

- анкетних оцінок учасників туристичного руху (лінгвістичні змінні l₁–l₅ за 17 критеріями у 3 групах G₁–G₃);
- прогнозованого рівня повторного відвідування регіону Ξ ∈ [0;1];
- експертного рівня безпеки регіональних туристичних систем Δ (терми Δ₁–Δ₅).

## 2. Функціональні вимоги

Користувач системи — **лише ОПР/аналітик** (туристи анкету онлайн не заповнюють; дані респондентів імпортуються масивом).

1. **Введення даних:** імпорт масиву респондентів з Excel/CSV (формат файлу «Експертне оцінювання.xlsx»: e_i, регіон, тип розміщення, K1–K17) + ручне введення/редагування окремих анкет аналітиком. Ξ та Δ для кожного регіону **вводяться вручну** ОПР.
2. **Довільна кількість регіонів:** регіони створюються/видаляються через інтерфейс, дані 3 областей — стартовий демонстраційний набір.
3. **Обчислення** за чотирма модулями (п. 4 нижче) з проміжними результатами на кожному кроці.
4. **Налаштування параметрів** (вимога розділу 4 — адаптивність): склад груп і критеріїв, шкала χ (15/30/50/80/100), параметри Z-сплайна, межі інтервалів a₁–a₆, пороги лінгвістичного трактування T_R.
5. **Редагування правил агрегації M_R1 через інтерфейс** (конструктор правил «Якщо–Тоді» з пріоритетом застосування). Реалізація поетапно: спершу фіксовані 5 правил зі статті як пресет за замовчуванням, далі — UI-редактор (узгоджено: «в ідеалі редагуються, але можна фіксовано»).
6. **Підтримка прийняття рішень:** якщо результат не задовольняє ОПР — повернення до налаштування параметрів і повторне оцінювання (цикл з рис. 4.1).
7. **Візуалізація:** дашборд порівняння регіонів, графіки функцій належності, розподіл терм-оцінок r*(e), кольорова шкала ризику R₁–R₅.
8. **Двомовний інтерфейс:** українська + англійська (i18n, перемикач мови; всі терми та звіти локалізовані).
9. **Експорт результатів** (PDF/Excel) — для додатків до дисертації.
10. **Автономність:** платформа не залежить від інших модулів системи розділу 5 (T₁–T₄ не реалізуються).

## 3. Архітектура та стек

```
┌────────────── Frontend: React + TypeScript ──────────────┐
│  Анкета │ Імпорт даних │ Панель ОПР │ Дашборд │ Параметри │
└──────────────────────────┬────────────────────────────────┘
                      REST API (JSON)
┌──────────────────────────┴────────────────────────────────┐
│            Backend: Python 3.12 + FastAPI                 │
│  ┌──────────────────────────────────────────────────────┐ │
│  │  Обчислювальне ядро (окремий пакет risk_core):      │ │
│  │  M_I → M_R1 → M_R2 → M_R3 → модуль прийняття рішень │ │
│  └──────────────────────────────────────────────────────┘ │
│  Імпорт Excel (pandas/openpyxl) │ Експорт звітів          │
└──────────────────────────┬────────────────────────────────┘
                  БД: SQLite → PostgreSQL
        (регіони, респонденти, оцінки, параметри, результати)
```

- **Backend:** Python + FastAPI — природний вибір для нечіткої математики (NumPy), читання реальних даних з Excel, автодокументація API (Swagger).
- **Frontend:** React + TypeScript, графіки — Chart.js або Recharts; i18n — react-i18next (uk/en).
- **БД:** SQLite на етапі розробки (нуль конфігурації), PostgreSQL за потреби.
- **Ядро — публічна бібліотека** (вимога керівника): окремий Python-пакет, напр. `tourism-risk` / `travel-risk-assess`, без залежності від веб-частини. Публікація на **PyPI** + код на **GitHub** (ліцензія MIT, README англійською з формулами та прикладами, docstrings, посилання на статтю для цитування — файл CITATION.cff). Веб-додаток використовує бібліотеку як залежність — інші дослідники й управлінці можуть застосовувати модуль у власних розрахунках без нашого UI.

### Розгортання демонстрації

Docker (compose: api + frontend + БД) → безкоштовний/дешевий хостинг для демонстрації в інтернеті (Render / Railway / Fly.io / VPS університету). Окремий публічний URL для захисту та апробації.

## 5. Модель даних (основні сутності)

- **Region** — регіон оцінювання (назва uk/en, Ξ, Δ); кількість довільна.
- **Respondent** — учасник руху (регіон, рік/місяць, тип розміщення).
- **Assessment** — оцінки респондента за K₁–K₁₇.
- **CriteriaGroup / Criterion** — довідник груп і критеріїв (відкритий — можна додавати).
- **PlatformConfig** — версія параметрів платформи (шкали, інтервали, пороги).
- **RuleSet / Rule** — правила агрегації M_R1 (пресет зі статті + редаговані ОПР, з пріоритетом і правилом за замовчуванням).
- **EvaluationRun** — результат обчислення: δ, φ, Ξ, m_S, ω, μ_R, T_R + збережені проміжні дані.

## 6. Інтерфейс (сторінки)

Усі сторінки — двомовні (uk/en), користувач — ОПР/аналітик.

1. **Регіони та дані** — створення регіонів, імпорт Excel, перегляд/фільтр респондентів, ручне додавання/редагування анкет.
2. **Панель ОПР** — введення Ξ і Δ по регіонах, запуск оцінювання, перегляд проміжних результатів по модулях.
3. **Дашборд** — порівняння регіонів, μ_R і T_R, графіки ФН, розподіл r*(e).
4. **Параметри** — редагування конфігурації платформи (з версіонуванням) та правил агрегації M_R1 (конструктор «Якщо–Тоді»).

## 10. Ризики проєкту

- **Неоднозначності формул** (у тексті розділу 4 є дубльовані позначення T/Δ, O_i/ω) — знімаються контрольним прикладом п. 8.
- **Повнота правил M_R1:** 5 правил можуть не покривати всі комбінації терм-оцінок — потрібен порядок застосування правил (зверху вниз, перше що спрацювало) + правило за замовчуванням (H).
- **Якість даних Excel** — потрібна валідація при імпорті (пропуски, діапазони 1–5).
